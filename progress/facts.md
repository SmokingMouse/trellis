# Verified Facts


- **CLI jsonl 里「长得像用户提问」的 user 消息有一半是 CLI 自己注入的，判据是结构字段而非文本前缀**（S84 实测，本机 400 个 jsonl / 1142 个 turn）：skill 触发的 `Base directory for this skill: …`、`<task-notification>`、Stop hook 反馈、`Continue from where you left off.`、Esc 打断的 `[Request interrupted by user]`（全库 522 条）、`/compact` 摘要 —— 全是 `type:"user"` 的纯文本消息，和真提问在结构上只差几个字段：`isMeta` / `promptSource === "system"` / `interruptedMessageId` / `isCompactSummary` / `isVisibleInTranscriptOnly`（真用户是 `typed`/`sdk`/`queued`，零命中）。把它们当 turn-start 的后果不是多个节点，是**把后续 assistant 的最终回复整段劫走**（实测 136 条僵尸 turn）。**反过来也是坑**：判据收严后，`claude --continue`/fork 出的 jsonl 链头上溯不到任何真 turn-start，整段回复会被静默丢弃（实测 117 条消息 / 16030 字符）——必须留「严格找不到主时用宽松判据兜底认领」这一层，且**次序不能反**。校验这类改动的守恒律是 **response 总字符数不许减**（只该换归属），不是「空 turn 变少了」。
- **在 attached CLI 会话里，`claude_session_id` 非空**不**等于「这节点是 import 建的」**（S84，被 critic 用沙箱 DB 打穿）：`app/api/chat/route.ts:512` 在**从非 tip 节点分叉**时会对 trellis 自建的临时节点执行 `setNodeResumeId`（`repo.ts:601`）写上 sid；而 `run-bus.ts:648` 的 `reconcileAttachedTurn` **只在 `stoppedWith === "done"` 时调用** —— run 被中止/报错就没有对账兜底，节点停在「非 streaming + 有 sid + 叶子」。任何拿 `claude_session_id IS NOT NULL` 当「import 产物」判据的删除逻辑都会吃掉用户打断的那一轮。**可靠判据是「节点 id 是否出现在源 jsonl 的 entry uuid 集合里」**：import 建的节点 id 恒等于某条 entry 的 uuid，trellis 自建的是本地 `crypto.randomUUID()`，两者不可能撞。
- **对镜像数据做「不在新集合里就删」之前，必须先确认源文件读得到**（S84）：`parseLineages` 原本把「jsonl 不存在」和「jsonl 是空的」都静默 `continue`，于是一条 lineage 失联就让 turn 集合残缺，清理会把那条 lineage 的节点整片剥掉。全部 lineage 都读不到时有 `parsedRows.length === 0` 早返回挡着，**唯独部分失败没有护栏**——而这恰恰是最常见的（CLI transcript 过期、用户清理、fork jsonl 被删）。本机实测：两个 attached 会话的源 jsonl **都已不在磁盘上**，所以这类会话的存量问题也修不了（走不到重解析路径），只能靠 UI 文案诚实交代。
- **`~/.claude/projects/**/*.jsonl` 是现成的高保真测试集**（S84）：解析器改动不用造 fixture，直接拿本机几百个真实会话跑统计（僵尸数 / 假 turn 数 / 文本总量 / 断链 parentId / 多次运行 hash 一致性）。比任何手写样例都能打 —— 本次两个关键 bug（注入劫持、兜底丢文本）都是它量出来的，mtime 排序取最近 N 个即可控制耗时。
- **代理层只用 curl 验证会漏掉 gzip 类 bug**（S77 实测，差点上 prod）：bun 的 `fetch` **自动解压**上游响应，且它自己会加 `Accept-Encoding`（客户端没要压缩也可能拿到 gzip 上游）。若把上游响应头原样透传，客户端收到的是「声称 gzip 的明文」+ 对不上的 `Content-Length`。**curl 默认不解压，一路 200 看不出任何异常；浏览器当场白屏卡死。** 写任何 HTTP 代理转发都要删掉 `content-encoding`/`content-length`/`transfer-encoding` 三个头，且**验证必须过一遍真浏览器或 `curl --compressed`**。
- **`Bun.serve` 的原生 WebSocket 可以做代理，`node:http` 的不行**（S77 实测）：`Bun.serve` 里 `server.upgrade()` + 以 `new WebSocket()` 连上游、逐帧转发，实测终端 shell 真执行命令；且同一个 `Bun.serve` 转发 SSE 是**真增量**（~4ms 开销，49 个 delta 跨 1154ms 未被缓冲），POST 体需 `duplex: "half"`。这是 trellis 能把「Next + WebSocket 服务」放在同一个端口同一个 cookie 闸后面的唯一办法。
- **bun 的 `node:http` `upgrade` socket 写不回客户端**（S77 实测，A/B 对照）：`server.on("upgrade", (req, socket) => …)` 里 `socket.destroyed=false`、`socket.writable=true`、`socket.write()` **返回 true**，但**客户端收到 0 字节**——静默吞掉；同一段代码 node v24.14.1 下客户端两次写入全收到。连带后果：`next.config` 的 rewrites 也不透传 WS upgrade（HTTP 部分 200，WS 超时零数据）。**所以 trellis（必须跑 bun）无法反代任何 WebSocket**——终端只能让浏览器直连 ttyd。与 `Bun.spawn({pty:true})` 同一种病：API 在、报成功、什么也不做。**下次想在 trellis 里代理 WS（S4 多租户必然撞上）先回来读这条。**
- **ttyd 不随父进程死，必须主动收尸；但「谁是孤儿」不能用 PPID 判**（S77 立，**S79 推翻判据并改写**）：kill 掉 trellis 后 spawn 出的 ttyd 仍在原端口 LISTEN 变孤儿，下次启动 `pickPort` 跳过被占端口漂到下一个 → 每重启泄漏一个进程 + 一个端口。**S77 用的判据是「`ppid == 1` 即孤儿」，这个假设在本机不成立**：实测 prod 正在服务的 ttyd（pid 25990）ppid 就是 1，而它的实例（`next start` pid 76269）活得好好的、子进程列表是空的（route handler 跑在会被回收的 worker 里，spawn 出的 ttyd 于是提前 reparent）。后果是**每起一个隔离测试实例都会 SIGTERM 掉 prod 的终端**——S77 那条「ttyd 互相残杀」只治了一半。现判据不猜进程树，改**显式登记**：拉起时把 `{ttydPort, pid, ownerPort}` 写进 `~/.trellis/ttyd/<port>.json`（ownerPort = 本实例 Next 的内部端口，server.ts 经 env `PORT` 下发，天然唯一），「主人还在不在」= 探那个端口有没有人监听；**没有登记的一律不杀**（认不出主人时保守放过，顶多占个端口）。另加「接管自己上一条命留下的 ttyd」：崩溃重启后不再新起一个，实测同 pid 复用、端口不漂。**tmux session 刻意不清**——它们活着正是「重启不丢终端」这个特性本身。
- **反向代理转发时必须改写 `Host`，否则 bun 的 fetch 会让网关自我循环**（S79 实测，**潜伏坑、非新引入**）：环境里存在 `http_proxy` 时（本机 clash 塞 `127.0.0.1:7897`），`fetch(url, {headers: req.headers})` 里的 `Host: 127.0.0.1:<网关端口>` 会盖过 URL 的 authority 决定连谁 → 网关把请求发回自己。症状极具误导性：`/` 和 `/login` 全部超时无响应，而**直接打内部 Next 端口一切正常、网关自己的 `/__gate/health` 也正常**；日志显示**一次 curl 触发几百次 fetch handler 调用**，user-agent 全是 curl。隔离到单个请求头：只带 `host` → 超时，去掉 `host` 的全套真实请求头 → 200。`HEAD~1` 的网关同样中招，prod 至今没炸只因 **launchd 不继承 shell 环境**（没有 `http_proxy`）——从开发 shell 里起的任何隔离实例都必中。**进程内 `delete process.env.http_proxy` 无效**（bun 在用户代码跑之前就把代理配置定死了），只能修在请求头侧：Host 换成上游 authority，原始值走 `x-forwarded-host`。实测 Next 16 的登录重定向发的是**相对 Location**，公网隧道的 `/login` 流程不受影响。
- **任何辅助进程打开 `~/.trellis/data.db` 都会判死正在跑的 run**（S79 实测）：`migrate()` 里藏着一段「把所有 `status='streaming'` 的节点改成 error」的收尸逻辑（`lib/server/sqlite.ts:531`），而 `migrate()` 是**每进程首次 `getDB()` 就跑**，不是「每次应用启动跑一次」。所以部署脚本查活跃 run 必须 `new Database(path, {readonly: true})` 裸查、绝不能走 `getDB()`；隔离实例（smoke / 测试）必须用 `TRELLIS_DB_PATH` 指到快照。顺带：`repo.ts:1900` 那个同名的 `reapInterruptedStreams()` 是**无人调用的死代码**，真正生效的是 `migrate()` 里的重复实现。
- **prod 跑在 `~/.trellis/current`（软链到 `~/.trellis/releases/<ts>-<sha>/`），仓库目录只是开发 checkout**（S79 切换完成，取代此前「prod 跑在 `python/learning/trellis`」那条）。上线只能走 `make deploy`；在任何 checkout 里 `make build` 都碰不到 prod，**S66 那条「build 后必须 kickstart prod」的前提已消失**。应急回滚 `~/.trellis/bin/rollback.sh`（自包含，不依赖仓库和 bun）。
- **运行期配置住在 `~/.trellis/shared/`，`git archive` 带不走未跟踪文件**（S79 真上线时踩爆）：认证凭证在 `.env.local` 里（bun 从 cwd 自动加载），被 `.gitignore` 忽略 → 第一个 release 里没有它 → `TRELLIS_AUTH_PASS` 缺失 → **网关的认证闸静默关掉**，而这台机器 `~/.cloudflared/config.yml` 配着 3088 的公网隧道。症状极隐蔽：服务活得好好的、所有页面都能开、健康检查全绿，**唯一的差别是日志里 `auth ON` 变成 `auth OFF`**。现在 `deploy` 的 `linkShared()` 会把 `~/.trellis/shared/` 下的文件软链进每个 release，smoke 带 cookie 验闸后页面 + **反向断言「无 cookie 的 `/api/sessions` 必须 401」**，verify 断言「闸不许 on→off」。**以后新增任何未跟踪的运行期配置，真源都要放 `~/.trellis/shared/`**，放 checkout 里等于下次部署就丢。
- **`launchctl bootout` 是异步的**（S79 实测，害 prod 停了约一分钟）：它返回时 job 未必真的消失，紧接着 `bootstrap` 会撞上还在的旧 job 报 `Bootstrap failed: 5: Input/output error`，然后服务就那么停着（`launchctl print` 查不到 = 已卸载但没装回来）。必须轮询 `launchctl print` 直到查不到再 bootstrap，并对 bootstrap 本身重试。手工救场：`launchctl bootstrap gui/$(id -u) ~/Library/LaunchAgents/<label>.plist`。

- **Tailwind 的 `group-hover:` / `[@media(hover:none)]:` 在 SVG 元素上照常生效**（S74 实测：`<g class="group">` 的子元素能吃到 group-hover；`@media (hover: none)` 块在编译产物里排在 `.opacity-0` / `.pointer-events-none` 之后，同特异性后来者胜 → 触摸设备上"悬停才显"的控件会常显可点）。所以 SVG 里的悬停控件不必走 React state。

- **从界面触发部署，子进程必须 `detached: true` 才活得过 switch**（S82 实测）：部署第七阶段 `launchctl kickstart -k` 杀的正是跑着 API 的那个进程；子进程留在同一会话里会被一起带走，于是 `verify` 和「验活失败自动回滚」两层安全网全失效，**坏版本原地留在 `current` 上**。实测证据：父进程 `spawn(..., {detached:true, stdio:["ignore",fd,fd]})` + `unref()` 后被 `kill -9`，子进程 `ppid` 变 1 并在父死后 6 秒照常写出结果。三个配套：① stdio 必须重定向到**文件**（父死后管道没人读，写日志会 EPIPE）；② 用 `process.execPath` 而不是赌 PATH 里有 `bun`（launchd 的 PATH 与登录 shell 不是一回事）；③ 派生前从 env 里删掉 `PORT`/`TRELLIS_NEXT_PORT`/`TRELLIS_TTYD_PORT`——它们描述「当前进程是谁」，带进去会让 smoke 起的临时实例继承 prod 的身份。

- **「tab 点不开」八成是流式渲染风暴卡死主线程，不是点击逻辑坏了**（S78 实测，swift-wren-91）：根因链 = ① store 的 `nodes` 是单个对象，流式期间每个 SSE 事件（catchup/tool_call_*）都 `{ ...s.nodes, [id]: {...} }` 换整个对象；② `LinearThreadView`/`Canvas` 都 `useSessionStore(s => s.nodes)` 订阅整个对象 → 每事件全树/全图重渲；③ `TurnCard` 流式态每帧对整段 response 跑 `rehypeHighlight`（几百 KB 是杀手）。三者叠加，长 run（百级 tool calls、几百 KB response）必卡死。**修法三件套**：tool_call 类事件用 `requestAnimationFrame` 合批成每帧一次 `set()`（终端事件 done/error 仍即时）+ 流式态 `REHYPE_STREAMING=[]` 不跑高亮（done 态再跑）+ `TurnCard` 加 `React.memo`。Canvas 侧若 `ChatNode` 已 `memo` 且 `layoutKey` 不跟 tool_calls 走，则天然免疫大半。诊断时先 `curl /api/sessions/[id]` 看节点数/tool_calls 量/response 大小，再看 store 事件提交频率，比在 UI 上瞎点靠谱。
